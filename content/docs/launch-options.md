Every command-line flag and environment variable the programs read, with its
default: `openac` (the client), `openac-launcher` (the launcher window),
`actool` (dat and image tools) and `plugincheck` (the plugin checker). It also
lists the files the client reads and writes, the console commands and the
keys, because those are how a running client is driven.

Diagnostic options are off by default and change no behaviour beyond what
they print or write. Options marked *test-only* are set by the test suite and
never by players. A new option is documented here in the same change that
adds it; `crates/openac/tests/launch_options_census.rs` fails when an
`OPENAC_*` variable named in the sources is missing from this page.

## The client, one session

`openac` with these flags (or none) plays one session. For several sessions,
or the launcher's way of starting a client, see the next section.

| Option | Binary | Default | Meaning |
|---|---|---|---|
| `--dat-dir <path>` | `actool`, `openac` | see `OPENAC_DAT_DIR` | The folder holding `client_portal.dat`, `client_cell_1.dat` and `client_local_English.dat`, and `client_highres.dat` when the install has it (optional; when present, an object it holds is read from it rather than the portal dat). Wins over the environment variable. In `openac` it is the folder the game window reads (each window opens its own reader when it opens) and where the game tables every session shares are read once at start (spells, spell components and their item classes, each magic school's focus, skills); without them spells have no names, enchantments do not count and skills have no attribute part (a `-- no game tables` notice says why). `openac run --config` takes the document's `process.content.datDirectory` first, then the variable. |
| `OPENAC_DAT_DIR` | `actool`, `openac`, the real-dat tests of `ac-dat`, `ac-render` and `ac-audio`, the `ac-render` and `ac-audio` examples, `scripts/check.*` | `%USERPROFILE%\Documents\Asheron's Call\` (`$HOME/Documents/Asheron's Call/` when `USERPROFILE` is unset) | The dat folder when no `--dat-dir` is given. The check scripts also run the real-dat tests (`--include-ignored`) when `client_portal.dat` is there. |
| `--headless` | `openac` | off | Run without any window support (no display needed). Without it the main thread runs the window host, and the console commands `/window` and `/close` open and close a game window on the running session. |
| `--server <host:port>` / `OPENAC_SERVER` | `openac` | `127.0.0.1:9000` | The login server; the connect port is this port + 1. The flag wins. |
| `--account <name>` / `OPENAC_ACCOUNT` | `openac` | none (required) | The account name. The flag wins. |
| `OPENAC_PASSWORD` | `openac` | none (required in this form) | The account password, from the environment only. A session-config document names a credential provider per session instead: an environment variable, standard input, or a file only its owner can read. |
| `--character <name>` | `openac` | none: wait at character selection | The character to enter the world with; the name match ignores case. Without it the session connects and waits at character selection: a window shows the connecting and selection screens, and the console's `/enter [character]` enters (headless too). |
| `--duration <seconds>` | `openac` | until Ctrl+C | Seconds in the world before a graceful log off. Ctrl+C (and on Unix SIGTERM and SIGHUP) always logs off gracefully. |
| `--log <level>` / `OPENAC_LOG` | `openac` | `info` | `error`, `warn`, `info`, `debug` or `trace`. |
| `--landblock-radius <n>` / `OPENAC_LANDBLOCK_RADIUS` | `openac` | from the display settings (High: `4`) | See [Graphics, streaming and sound](#graphics-streaming-and-sound). The flag wins; `openac run --config` reads only the variable. |
| `OPENAC_DATA_DIR` (one-session form) | `openac` | the install root | The data folder for `/log` files and journals in this form; it follows the same rules as in `openac run` (see the next section). |
| `-h`, `--help` | `actool`, `openac` | — | Print usage. |
| `openac peer-hub <folder>` | `openac` | — | The peer hub the sessions on this computer share for plugin peers. A session starts it when a plugin first subscribes and no hub answers, at `<folder>` (the sessions' peer folder; a named pipe for the current user on Windows, a Unix socket in the folder elsewhere). One hub per user and folder (a second exits at once); it exits 15 s after its last client leaves. Not meant to be typed. |
| `openac plugin-api` | `openac` | — | Print the plugin API versions this client loads, one line of JSON: `{"schemaVersion":1,"minimum":"1.0","current":"1.12"}`. Every release carries this output as `plugin-api.json` beside `openac` (in `OpenAC.app`, under `Contents/Resources`), and the launcher installs, updates and lists plugins by the installed client's file (a client released before the file, 0.2.3 and older, by its version; one without the file whose version is not such a release has an unknown range, and the launcher installs nothing for it). A client run beside a developer-built launcher has no file unless it is written there (`openac plugin-api > plugin-api.json` in that folder). |

## The client, session-config documents

```text
openac --help
openac validate --config <path> [path overrides]
openac run --config <path> [path overrides] [console options] [credentials]
openac --session-config <path> [--console]
```

Every option except `--console` takes a non-blank value and appears at most
once; an unknown option is refused (exit 2). `validate` loads and checks the
document and resolves the folders without connecting, then prints
`Configuration valid: version 1, N session(s).`

| Option | Binary | Default | Meaning |
|---|---|---|---|
| `validate` / `run` | `openac` | — | Check the document only, or run its sessions. |
| `--config <path>` | `openac` | none (required) | The session-config document (versioned strict JSON, below). |
| `openac run --config <file> [--console] [--config-dir/--data-dir/--cache-dir <dir>] [--user <a> --password <p>]` | `openac` | — | Run every session in the document, each on its own thread. With window support (the default when a display exists) the console's `/window [id]` opens the game window on that session or moves it there (no id: the chosen session, as for `/objects [id]`; an id no session has prints `no session is called <id>`), and `/close` closes it; without window support (`OPENAC_HEADLESS=1`, or no display) `/window` prints `no window support in this process ...`. `/sessions`, `/session <id>` (where unaddressed lines go; the first session at start), `@<id> <line>` (one line to one session, only when that id runs; otherwise `@` lines are server commands), `/objects [id]`, `/time [id]`, `/contracts [id]`, `/journal [id]` and `/quit [id]` also work, and every other line is chat for the chosen session (see [console chat lines](#the-console-chat-commands-and-keys)). With `--console`, chat prints on the console stream, each line behind `[id]` when several sessions run. Ctrl+C, Ctrl+Break, and on Unix SIGINT, SIGTERM and SIGHUP (a closed terminal, even under `nohup`) log every session off, then the process exits, with or without the console, and also when the reader of its output has gone (lines to a closed pipe are dropped). On Windows a process whose parent ignores Ctrl+C (one started in a new process group) never receives it; Ctrl+Break always arrives. Exit codes below (6 also when a session monitor failed). |
| `openac validate --config <file>` | `openac` | — | Check a session-config document without connecting. |
| `openac --session-config <file> [--console]` | `openac` | — | The launcher's windowed start: exactly the flag and the path, and optionally `--console`. It reads the document as a window does (exactly one session; the character may be absent, and then the session waits at character selection with the window showing the connecting and selection screens; `policy` is ignored; `"mode": "probe"` is refused), resolves the password from the provider it names (the launcher writes one line to standard input), opens the game window on the session at once, writes the session's `statusFile` as `openac run` does, and takes the dats from `process.content.datDirectory`, else `OPENAC_DAT_DIR`. Ctrl+C, Ctrl+Break, and on Unix SIGINT, SIGTERM and SIGHUP log the character off, then the process exits; so does closing the window (or the window failing). With `--console` (how the launcher starts it) the console reads typed lines as `openac run --console` does (`/close` closes the window and the session plays on, `/window [id]` opens it again, `/quit` logs off) and chat prints on standard error; then only a window that fails or that `/close` closes leaves the session playing headless, while the player closing the window still logs off and exits. Exit codes: 0 graceful, 2 usage, 3 configuration, 4 credential, 5 connection, 6 runtime or no window support. |
| `--root-dir <path>` | `openac` | see `OPENAC_ROOT_DIR` | The whole install folder: settings in `settings/`, and data, plugins, logs and cache beneath it. Wins over `process.paths.rootDirectory` and replaces the document's whole folder set; the environment and the pointer file are not consulted. A member flag below still wins for its own member. |
| `--config-dir <path>` | `openac` | see `OPENAC_CONFIG_DIR` | The settings folder (`<root>/settings`); wins over the document's `process.paths.configDirectory`. Credential files resolve against it. |
| `--data-dir <path>` | `openac` | see `OPENAC_DATA_DIR` | The data folder, which is the install root itself (the prepared game content in `game/`, plugins in `plugins/`, each plugin's saved files in `plugins/<id>/data`, the shared VTank profiles in `plugins/acdream.mosstank/vtank/`, session folders, chat logs and crash reports in `logs/`). Wins over `process.paths.dataDirectory`. |
| `--cache-dir <path>` | `openac` | see `OPENAC_CACHE_DIR` | The cache folder (`<root>/cache`: diagnostics, plugin peer notes, and `plugin-modules`, each plugin compiled to machine code, one file per plugin build and client build, named by their hashes; a damaged or stale file is ignored and rebuilt, and the folder is safe to delete: the next start compiles again). Wins over `process.paths.cacheDirectory`. |
| `--console` | `openac run` | see `OPENAC_HEADLESS_CONSOLE` | Read typed lines and print chat. |
| `--console-stream <stdout\|stderr>` | `openac run` | see `OPENAC_HEADLESS_CONSOLE_STREAM` | Where the console prints. |
| `--user <account>` / `-user` with `--password <password>` / `-password` | `openac run` | — | Direct credentials for a one-session document: both or neither; they replace the session's account and credential. The password is visible to other local users in the process list; prefer a credential provider. |
| `OPENAC_ROOT_DIR` | `openac`, `openac-launcher` | the pointer file, else `%LOCALAPPDATA%\openac-rust` on Windows, `~/Library/Application Support/openac-rust` on macOS, `$XDG_DATA_HOME/openac-rust` (`~/.local/share/openac-rust`) elsewhere | The install root when no flag or document names one. The launcher sets it (and the three member variables) for every client it starts. The folder name differs from the retired C# client's (`OpenAC`) so the two programs never share an install. |
| `root.json` (pointer file) | `openac`, `openac-launcher` | absent | `{ "version": 1, "root": "<absolute folder>" }` in the default root names the install root when neither the command line, the document nor `OPENAC_ROOT_DIR` does. A pointer that cannot be understood is a configuration error (exit 3), never a silent fallback. |
| `OPENAC_CONFIG_DIR` | `openac`, `openac-launcher` | `<root>/settings` | The settings folder alone, when neither a flag nor the document names one; wins over `OPENAC_ROOT_DIR` for its member. Ignored under an explicit root. Blank counts as unset. |
| `OPENAC_DATA_DIR` | `openac`, `openac-launcher` | `<root>` | The data folder (the root itself) alone, with the same precedence. |
| `OPENAC_CACHE_DIR` | `openac`, `openac-launcher` | `<root>/cache` | The cache folder alone, with the same precedence. |
| `OPENAC_HEADLESS_CONSOLE` | `openac run` | on when standard input is a terminal | `0` turns the console off, anything else on; `--console` always turns it on. |
| `OPENAC_HEADLESS_CONSOLE_STREAM` | `openac run` | `stderr` | `stdout` or `stderr` (any case); anything else is a configuration error (exit 3). `--console-stream` wins. |
| `OPENAC_HEADLESS` | `openac run` | unset | `1` runs the document's sessions without window support. The launcher sets it only for a character refresh; its headless play sessions keep window support so their row can open a window. Without it, while no window is open the process holds only the window host's event loop (memory as with `1`); the GPU device, window and world renderer are made by the first `/window`, and about 290 MB of them stays after that window closes. |
| `OPENAC_STATUS_HEARTBEAT` | `openac` (both forms) | unset | `1` makes each session write a `heartbeat` line to its status file every 10 s in which its loop made progress and, while the game window shows it, the window's event loop answered too (a minimized window still answers; a hung one does not). The launcher sets it for every client it starts and shows a client in the world that stays silent for 30 s as "Not responding". Unset, nothing is written, so a launcher that does not know the event never sees it. |
| `OPENAC_CONSOLE_KINDS` | `openac` (both forms, with the console) | unset | `1` begins every console line a player would see with a mark of its kind: the record-separator character (U+001E) and one letter, `c` a line the main chat window shows (every line of a message the server broke into several), `s` the status box's text (`[client] ...`), `t` a line typed into the console (echoed, once, as typed), `r` the console's own answers (`/sessions`, usages), a confirmation for the player to answer, and the answers a session gives within 5 s of a line typed on its console (lists and views such as `/objects`, `/time`, `/inv`, `/appraise` of the player's own question, `/corpses`, `/spells`, `/sheet`, `/where`, the selection, the fellowship, the character list, a move's end, and refusals). The same events at any other time (a plugin's quiet identify, a command a plugin or bot policy ran) stay unmarked, as does everything else (the session's life, portal space, plugins, the window, diagnostics). The launcher sets it for every client it starts and strips the marks; a person reading the console in a terminal never sees one, but the lines of a launcher-started client's `client.log` (its session folder) may begin with U+001E and a kind letter. |

Exit codes: 0 success, 2 usage, 3 configuration, 4 credential, 5 connection,
6 runtime.

### The document

Version 1. Member names are case-sensitive; unknown or repeated members,
comments and trailing commas are refused:

```json
{
  "version": 1,
  "process": {
    "paths": { "rootDirectory": "...", "configDirectory": "...", "dataDirectory": "...", "cacheDirectory": "..." },
    "content": { "datDirectory": "C:\\AC", "preparedAssetPath": "C:\\AC\\openac.pak" }
  },
  "sessions": [
    {
      "id": "bot-1",
      "endpoint": { "host": "127.0.0.1", "port": 9000 },
      "account": "myaccount",
      "character": { "index": 0 },
      "policy": { "id": "idle" },
      "credential": { "provider": "environment", "reference": "OPENAC_BOT_PASSWORD" },
      "statusFile": "bot-1-status.jsonl"
    }
  ]
}
```

- `sessions[].character`: exactly one of `index` (from 0), `id` (non-zero) or
  `name`. `"mode": "probe"` instead of `character` and `policy` connects,
  reads the character list and never enters the world.
- `sessions[].policy.id`: `idle` (enter and stay), `portal-route-smoke`
  (an admin character: `@teleloc` to Aerlinthe, Caul and Rynthid, then a
  lifestone recall, each arrival in exactly its cell and followed by 4 s
  running, a 2 s right turn and 4 s running, then log off and exit 0; an
  arrival elsewhere ends the session as a failure, exit 6), `lifecycle-smoke`
  (enter, say a line, recall to the lifestone, wait for the arrival,
  reconnect, enter again, then log off and exit 0), `observer-movement`
  (an admin character: `@teleloc` to cell `0xF6820033`, say a line, then turn
  right for 1.25 s and run for 4 s, over and over; never ends; a teleport
  that lands elsewhere logs it off with exit 6) or `jump-probe` (charge a
  jump for 0.6 s, release it, press jump again for 1 s once airborne,
  printing each airborne transition; logs off when done, or 3 s after a
  release that never left the ground); any other id is a configuration error
  (exit 3). The policy sees every session event, is stepped on the host's
  clock at least every 50 ms, and its commands carry the generation they
  were made in.
- `sessions[].credential.provider`: `environment` (the variable named by
  `reference`), `standardInput` (one line per session, in document order) or
  `file` (relative to the config folder; on Unix readable only by its owner;
  never a symbolic link). The reference must be unique per provider.
- `sessions[].statusFile`: one JSON line per session event (`started`,
  `connected`, `characterList`, `enteredWorld`, `characterCreated`,
  `creationFailed`, `pluginLoaded`, `pluginFailed`, `loginCommandFailed`,
  `disconnected`, `exited`), and, in addition to OpenAC's events, the game
  window on the session: `windowOpened`, `windowClosed` (`reason`:
  `requested`, `closedByUser`, `renderFailed`, `shutdown`) and
  `windowFailed` (`error`; a `/window` the client could not carry out, such
  as one without window support). Also added: `heartbeat` (the envelope
  only), written every 10 s while the session and its window make progress,
  only when `OPENAC_STATUS_HEARTBEAT` is `1` (the launcher sets it); and on `exited`, when
  a refusal from the server ended the session, `serverMessage` (the game's
  words for it) and `accountInUse: true` when it refused the login, before
  the session got in, saying the account or one of its characters is still
  logged on (an earlier session the server has not let go of yet; the same
  code in the world is a boot and does not count).
- A server silent for more than 140 s is gone (not configurable). A session
  with no window attached at that moment writes `disconnected` with reason
  `connection-lost` and logs in again every 30 s, entering its configured
  character as at start, until an attempt gets back in (each failure prints
  a notice; an account without that character ends the session); its
  plugins hear the log off, then the next login. A session a window shows
  ends instead (`disconnected` with the reason, exit 5). While it waits,
  `/quit` ends it and `/window` is kept for the next connection; other
  requests are refused.
- `sessions[].characterOptions`: declarable option names (the 26 that can be
  declared: what the character accepts, fight options, chat rooms) to `true`
  or `false`. Once the server has sent the character's options and login
  complete is out, each option that differs is changed as the options panel
  would change it (an option the game saves at once, at once; the rest with
  one block save after); undeclared options are left alone. A reconnect
  checks again.
- `sessions[].loginCommands`: lines typed into the chat box after entering
  the world (chat, client commands, `@` server commands, the client's own
  verbs such as `/nav`). The first goes once the server is listening (login
  complete sent) and the session's plugins have heard the arrival and ticked
  once since; each next one `loginCommandDelayMs` (default 500) after the
  last; every new generation runs the list again. A line the chat box cannot
  route writes a `loginCommandFailed` status line and the list goes on.
- `plugins`, `pluginTags`, `pluginSettings`: see [Plugins](#plugins).
- `sessions[].remote` (optional): a relay the session offers itself to, so it
  can be shown and played somewhere else:
  `{ "url": "wss://…", "enabled": true, "credential": { "provider": …, "reference": … } }`.
  The client dials out to `url` (a `wss://` address; `ws://` only for this
  computer) and keeps the link open; the credential names where the
  session's token for the relay comes from, read as the login credential is,
  so the token is never in the document. `enabled` (optional, default
  `true`) set to `false` keeps the block without connecting. Without the
  member, and without a setting made with `/remoteac` (below), nothing
  connects anywhere. A relay can never stop a session: an address or token that
  cannot be used, a relay that is down, a lost link or a closed remote
  window leave the session playing, with a line on the console when the
  endpoint could not start. A remote window that takes control loses it
  after a second without input, and the movement keys are let go. Not
  started for `mode: "probe"`.
- `/remoteac`, typed in the chat box, on the console or as a login command,
  sets the remote window while the session runs; it never reaches the
  server, the plugins or the chat. `/remoteac url "<wss url>"` sets the
  address (the same rules as `url`), `/remoteac secret "<token>"` the token
  (answered `secret set` only, never recalled with the up arrow, and
  starred out in the draft an attached browser sees while it is typed),
  `/remoteac enable` and `/remoteac disable` connect and leave (a browser
  attached is let go; the address and token are kept), and
  `/remoteac status` says whether it is on, the address, the link
  (connected, refused or trying again) and whether a browser is attached,
  never the token. A session whose document has a `remote` block keeps the
  settings in that block. Every other session keeps them in
  `<config>/remote.json`, by server, account and character, since the
  launcher writes a new document for every start; that file holds where
  the token is, never the token. The token is written to
  `<config>/remote/<server>/<account>/<character>.token`, readable only by
  its owner on Unix. Turned on in the middle of a session, a browser sees
  the world from that point on.
- `process.content.preparedAssetPath` and the overlay members are parsed and
  checked but not used: this client reads the dats directly and has no
  prepared asset package.
- A window started on a document (`openac --session-config`) requires
  exactly one session, allows the character to be absent, ignores `policy`
  and refuses `"mode": "probe"`.

## Folders and files

| Option | Binary | Default | Meaning |
|---|---|---|---|
| the install's folders | `openac`, `openac-launcher` | — | Beneath the root: `app/` (client versions, launcher update), `settings/`, `game/` (the prepared game content and its records), `plugins/<plugin id>/` (the plugin's code, and the player's `data/` for it; MossTank's folder also holds the shared VTank profiles, `vtank/`), `logs/`, `screenshots/`, `journal/` and `cache/`. `layout.json` (`{ "version": 2 }`) says the root is in this layout. |
| moving an older install | `openac`, `openac-launcher` | at start | The launcher and every client (windowed or not) move an install from the layout before `layout.json` once, before reading any of it: `data/` becomes `game/` (and the content records name the moved files), each plugin's `files/` becomes its `data/`, `vtank/` moves to `plugins/acdream.mosstank/vtank/`, MossTank's old `debug/macro-*.log` files move to `logs/old plugin logs/`, and the old session folders in `logs/launcher/` are deleted when older than 7 days, else moved to `logs/<server>/<character or account>/<local start time>/` (keeping their `client.err.log`; one that cannot be read goes to `logs/unsorted/`). A file that would land on another keeps the newer in place and the other beside it as `<name>.old<ext>`. The mover holds `layout.lock` in the root and takes the install's session lock alone, so it never runs while a client of the install runs, nor twice at once: the launcher shows "Waiting for N clients to close before moving files" and goes on when they have. A client waits up to 10 s for another program that is moving the files; a client that finds the install held by others (an older launcher's session, an older client) does not wait and exits 3 with "This client needs the new launcher. Restart the launcher to finish the update." Folders reached through a link (a symbolic link or a junction) are moved through it; between two volumes each file is copied under a temporary name (`<name>.copying`, removed at the next start if a copy was cut short), checked byte for byte, renamed into place, and only then is the original deleted. A file identical to the one already there is not kept twice; a link that leads back into a folder being moved is removed rather than followed. A step that cannot finish stops it: "Could not move your files to the new layout: <path> is in use. Close all OpenAC clients and start the launcher again." when a file is held open, otherwise the path and the error itself. The launcher moves the files with its window open ("Moving your files to the new layout…"); closing it during a move waits for the move to finish ("Finishing the move…"). After a failed step it starts no client and offers Try again and Check for a launcher update (installing a newer launcher that can finish the move; it takes over only once no move runs); a client exits 3; the next start goes on from there. Nothing reads the old places afterwards. The launcher never starts, and never rolls back to, a client released before this layout (older than 0.1.10): when the client beside the launcher (its own build) is there it starts that one instead, otherwise it says "Update the client". |
| session folder | `openac-launcher`, `openac` | one per launcher-started session | `logs/<server>/<character>/<yyyy-MM-dd HH-mm-ss>/` (the local start time; ` (2)`, ` (3)` after it for a second session of the same character in the same second): the session document `session.json`, the status file `status.jsonl`, `client.log` (the client's standard output and error, 2 MiB per file, rotating to `client.log.1` through `.3`), and `plugins/<plugin id>.log`. `<server>` is the launcher's name for the server and `<character>` the character's, or the account's for a session started at character selection or a character refresh. Names are made file-name safe (`<>:"/\|?*` and control characters, and trailing dots and spaces, become `_`; a device name such as `CON` gets a `_` after it; a server named `crash`, `launcher`, `old plugin logs` or `unsorted` too). The session id stays the launcher's `<utc time>-<32 hex>` and is recorded in the files. A client learns its folder from the session document's place; a client started by hand has none. |
| launcher log `logs/launcher/launcher.log` | `openac-launcher` | always | The launcher's own lines (its start, the folder move and cleanup, its window's GPU reports, the control endpoint) and each session's state changes and errors, with the local time, appended across starts; past 4 MiB it becomes `launcher.old.log` (replacing the one before). |
| log cleanup | `openac-launcher` | at start, after the move | Session folders whose start is more than 7 days ago (never one a running client holds), crash reports and files in `logs/old plugin logs/` last written more than 7 days ago are deleted; server and character folders left empty go too. A deletion that fails is written to the launcher log and skipped. ## The launcher

`openac-launcher` starts `openac` sessions (see `openac --session-config` and
`openac run` above). A startup error exits 74 and writes
`<root>/logs/crash/launcher-crash-<time>.log`. Every client and windowless
host holds the install's session lock (`<root>/app/.update-session.lock`)
shared for its whole run and refuses to start (exit 3) while an update or a
move of the install folder holds it exclusively.

| Option | Binary | Default | Meaning |
|---|---|---|---|
| `--root-dir <path>` | `openac-launcher` | the resolved root (see `OPENAC_ROOT_DIR`; the launcher and the client share it) | The whole install folder, absolute; the environment and the pointer file are not consulted. The profiles (`launcher-profiles.v3.json`, passwords in plain text; an older launcher's `launcher-profiles.v2.json`, or else `launcher-profiles.json`, is read once to migrate and never written) the remembered ticks (`launcher-checked-accounts.json`) and whether checked clients are kept running, with the relaunch delay (`launcher-relaunch.json`), and the consoles' Verbose (`launcher-console.json`) live in `settings/`; the content record (`retail-content.json`) and prepared content in `game/`; the client store, installed-plugin records and launcher update in `app/`; plugins in `plugins/`; each session's files in its session folder under `logs/` and the launcher's own log in `logs/launcher/launcher.log` (see "Folders and files"); the plugin list cache and icons, and the saved known server list (`known-servers.json`, `known-servers-players.json`), in `cache/`. |

## `actool` commands

Arguments are parsed with the standard library only. Ids are hex, with or
without `0x`. Floats print as their shortest decimal form followed by their
bit pattern. `--dat-dir` and `OPENAC_DAT_DIR` (above) name the dats.

| Command | Prints |
|---|---|
| `actool dat info` | Header fields, iteration and entry counts of every dat. |
| `actool dat landblock <id>` | A landblock (`XXYYFFFF`): terrain words and heights, then its objects and buildings. |
| `actool dat setup <id>` | A setup (`02......`): parts, locations, placement frames, shapes, lights, default tables. |
| `actool dat motiontable <id>` | A motion table (`09......`): stance defaults, cycles, modifiers and links with their animations. |
| `actool dat envcell <id>` | An interior cell (`XXYYNNNN`, `NNNN` from `0100` to `FFFD`): flags, position, surfaces, portals, visible cells, static objects; then its cell shape from the environment (vertices, polygons, portals, tree sizes). |
| `actool dat region <id>` | A region (`13......`; the game's is `13000000`): land and height table, calendar, sky, ambient sound, scenery and terrain textures. |
| `actool dat layout` | One line per UI layout (`21......`, local dat): root element id, type and size, element count and type histogram. |
| `actool dat layout <id>` | A UI layout (e.g. `21000006`, the chat window): every element with type, rectangle, z level, read order, edge modes, default state and base element, then each state's media and properties. |
| `actool dat font <id> [--out <base>]` | A font (`40000000`..`40000FFF`): metrics and every glyph. With `--out`, writes `<base>-fg.png` and `<base>-bg.png` (the atlases, alpha as grey, 4x) and `<base>-sample-6x.png` (a sample line drawn with outline and fill, 6x). |
| `actool dat gfxobj <id>` | A model (`01......`): flags, surfaces, vertices, polygons and every BSP node. |
| `actool dat texture <id> --out <file.png>` | A texture decoded to PNG: a render surface (`06…`/`07…`), a surface texture (`05…`, its first image) or a surface (`08…`, with its clip-map and additive bits; a solid surface gives a 1×1 image). |
| `actool dat edges <id>` | A render surface's four first and four last columns as RGB hex, top to bottom (seams between tiles). |
| `actool dat sprites <id,id,...> --out <file.png>` | Render surfaces left to right on a grey strip (6 px apart and around, blended over it), zoomed 10x, and their sizes in order. |
| `actool dat vitals-bars` | The first layout holding the vitals health meter (`0x100000E6`), then the images of each meter (health, stamina, mana) with their element, state and draw mode. |
| `actool dat vitals-layouts` | Every layout holding a vitals meter (`0x100000E6`/`EC`/`EE`) with its size (dump one with `dat layout <id>`). |
| `actool dat mock-selbar --out <file.png>` | The selected-object health bar (back `0x0600193E`, fill `0x0600193F`) at fills 1.0, 0.9, 0.7, 0.5 and 0.0, one row each, cropped from the left and blended over a dark canvas, 8x. |
| `actool image compare <expected.png> <actual.png> <out.json> [tolerance=2] [max-fraction=0.001] [mask.png]` | Compare two screenshots pixel by pixel: a pixel differs when a channel is more than the tolerance apart; pixels where the mask has alpha are skipped. Writes a JSON report in OpenAC's format; exit 1 when the different fraction is over the limit. Needs no dats. |
| `actool image crop <in.png> <x> <y> <w> <h> <zoom> <out.png>` | A region of a PNG (clamped into it), zoomed by repeating pixels. |
| `actool image probe <in.png> <x0> <y0> <x1> <y1>` | A block of a PNG's pixels as RGB hex, one line per row. |
| `actool frames summarize <history.csv> <checkpoints.jsonl> <markers.log> <out.json>` | Summarise an `OPENAC_FRAME_HISTORY` CSV: the whole route, the 5 s before each checkpoint (one JSON object per line: `name`, `timestampUtc`, `resources.processTotalAllocatedBytes`) and 10 s before to 5 s after each `<utc> materialized destination='<name>'` log line, with p50/p95/p99/p99.9, maxima and the worst frames. |
| `actool migrate-classic [--vtank <dir>] [--ub <dir>] [--root <openac-root>] [--overwrite] [--dry-run]` | Copies a classic VirindiTank and UtilityBelt setup into the install's `plugins/acdream.mosstank/vtank/mosstank/` folder, where MossTank reads it, printing one line per file and a summary. ## `plugincheck`

The plugin checker for plugin authors: the launcher's own install rules, then
the plugin's WebAssembly module loaded without running it. See
[Writing a plugin](@/docs/plugin-development.md).

| Command | Does |
|---|---|
| `plugincheck <path> [--json]` | Checks an unzipped plugin folder (a hand install) or a plugin `.zip` (a release asset): `plugin.json` present and read by the client's parser (an OpenAC C# manifest fails as "built for OpenAC (C#)"), the launcher's install rules, and, for a folder, the direct-install checks; for a zip, the 64 MiB cap, safe extraction within the launcher's limits, the content policy (`.wasm .json .xml .txt .md .png .ttf .otf`, the entry module present), the icon (64 x 64 PNG, at most 64 KiB), the `<zip>.sha256` file beside it (skipped when absent) and the release asset name `<id>-<version>.zip` (noted when different). Then the entry `.wasm` is loaded (never run) and checked as a session does: its `openac.api` section names the manifest's API version, its `openac.layout` section holds this client's record layouts for everything it uses (else "built against a different plugin API layout; rebuild it against this client's SDK"), every import is a client function the declared permissions allow, and the calling convention's exports are there; it lists the permissions used and any declared but unused. One `[PASS]`/`[FAIL]`/`[SKIP]` line per check, a failure with its fix; `--json` prints one JSON object (`schemaVersion`, `mode`, `path`, `verdict`, `checks[]` with `check`, `status`, `message`) and nothing else. Exit 0: it would install; 1: it would be refused; 2: usage, a missing path, or a file that is not a `.zip`. |
| `plugincheck pack <plugin folder> <out dir>` | Writes the folder's release assets into `<out dir>`: `plugin.json`, `<id>-<version>.zip` (every file of the folder, manifest at the root, Finder/Explorer metadata files left out; the same folder always packs to the same bytes), `<id>-<version>.zip.sha256`, and `icon.png` when the folder has one; then checks the zip it wrote and prints the tag to publish them under (`wasm-v<version>`, not marked latest). A manifest the launcher would refuse writes nothing (exit 1). |
| `plugincheck pack <plugin folder> <out dir> --index <file>` | For a repository publishing several plugins: packs as above under the tag `wasm-<id>-v<version>`, then sets the plugin's entry in the plugin index `<file>` (started when it does not exist, every other entry kept; an entry already naming a higher version on that channel, as when packing a hotfix of an older line, is left as it was and the command says so) and says to upload it as `plugins-index.json` to the `wasm-index` release. An existing index the launcher would refuse writes nothing (exit 1). |
